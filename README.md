# Bank Intelligence Platform

Единая платформа, объединяющая два проекта в одно приложение, одну базу PostgreSQL и один API:

| Источник | Модуль | Что даёт |
|---|---|---|
| [`dilshod544/kassa-`](https://github.com/dilshod544/kassa-) | **Cashier Intelligence** | Аналитика кассиров: KPI, нагрузка, БЭК/ФРОНТ, статусы, отпуска, замещения, дисциплинарные взыскания |
| [`grxt777/arena-test`](https://github.com/grxt777/arena-test) | **ATM Monitor** | Реестр банкоматов и филиалов, остатки, карта, прогноз и маршруты инкассации |

---

## Что даёт объединение

* **Одна база вместо двух.** Оба домена (`atms`, `branches` и `cashier_*`) живут в одной базе PostgreSQL `bank_intelligence`; данные сборщика ATM — в схеме `atm_monitor` той же базы. Таблицы создаются автоматически при старте.
* **Одно приложение и один порт.** Раньше это были два независимых FastAPI-сервера с одинаковыми путями `/api/cashiers/*`, которые конфликтовали. Теперь — один `api/main.py` со сквозным набором эндпоинтов.
* **Один дашборд.** Общий хаб `/dashboard/index.html` с живыми показателями обоих модулей и перекрёстной навигацией между картой ATM и аналитикой кассиров.
* **Единый центр импорта.** `/dashboard/import.html` — выбор между реестром банкоматов, реестром филиалов и отчётами кассиров.
* **Сохранена «продвинутая» версия каждой фичи.** Там, где функциональность пересекалась, взят более развитый вариант — см. таблицу ниже.

### Как разрешены пересечения

| Фича | Решение |
|---|---|
| Аналитика кассиров | Взята модульная версия из `kassa-` (`core/cashier/`: helpers / parsers / repository / analytics) вместо однофайловой из `arena-test` — она умеет HR-статусы, замещения, филиалы, взыскания и фильтры |
| Импорт кассиров | Взят «Единый центр импорта» из `kassa-` (drag & drop, выбор отчётного месяца) |
| База данных | PostgreSQL (psycopg 3 + пул соединений). Нативные типы: `TIMESTAMPTZ`, `DATE`, `JSONB`, `BIGINT`, внешние ключи с `ON DELETE CASCADE`, upsert через `ON CONFLICT` |
| Конфигурация | Объединена: путь к базе + бизнес-пороги ATM (`LOW_CASH_PCT`, `DEFAULT_CAPACITY`, параметры маршрутов) |
| Главная страница | Написан новый общий хаб, объединяющий разделы обоих проектов |

### Исправления, сделанные при объединении

* **Долгота ATM терялась при импорте.** В реестре две колонки с одинаковым заголовком «Геолокация» (широта и долгота); вторая отбрасывалась как дубликат, из-за чего маршруты инкассации не строились. Теперь второе вхождение корректно трактуется как `lon`.
* **Жёстко зашитый `localhost:8000` во фронтенде.** Все страницы переведены на `location.origin` (и `wss://` для WebSocket), поэтому дашборд работает за обратным прокси и на любом домене.

## Быстрый старт

```bash
./run.sh
```

Скрипт установит зависимости, при необходимости запустит PostgreSQL
(Homebrew), освободит порт 8080, если его занял прошлый запуск, и поднимет
сервер. Откройте <http://localhost:8080>.

База берётся из `DATABASE_URL` (в `.env` или окружении), по умолчанию
`postgresql://localhost:5432/bank_intelligence`. Если такой базы ещё нет,
приложение создаст её само, а таблицы — при первом старте.

Полезные переменные:

```bash
APP_PORT=8081 ./run.sh                                     # другой порт
DATABASE_URL=postgresql://user:pass@host:5432/db ./run.sh  # другая база
```

### Windows

Двойной клик по `start_new_pc.bat` (или `start.bat` — то же самое). Права
администратора не нужны. При первом запуске скрипт сам скачивает в папку
проекта портативный Python 3.13 (если в системе нет Python 3.13) и портативный
PostgreSQL 16 (~320 МБ), создаёт базу в `data\pgdata` и поднимает её на порту
5433; повторные запуски стартуют сразу. Если в `.env` задан `DATABASE_URL`,
используется указанная база, а портативный PostgreSQL не скачивается.
Браузер открывается сам, когда сервер действительно готов. Сервер слушает
только `127.0.0.1`; для доступа с других компьютеров перед запуском выполните
`set APP_HOST=0.0.0.0`.

### Требования

* Python 3.13
* PostgreSQL 13+ (macOS: `brew install postgresql@16 && brew services start postgresql@16`)
* Всё остальное ставится из `requirements.txt`

### Перенос данных из старой SQLite-версии

Если остались файлы `data/bank.db` / `data/atm_monitor.db` от прежней версии:

```bash
PYTHONPATH=. python3 migrations/sqlite_to_postgres.py \
    --sqlite data/bank.db --atm-monitor-sqlite data/atm_monitor.db
```

Скрипт переносит все таблицы с приведением типов, выравнивает
последовательности id и в конце сверяет количество строк по каждой таблице
(код выхода 2 при расхождении). `--replace` — очистить целевые таблицы перед
переносом, `--reset-admin-password` — выдать admin новый пароль.

### Частые проблемы

| Симптом | Решение |
|---|---|
| `Address already in use` | `./run.sh` сам освободит порт. Иначе: `lsof -ti:8080 \| xargs kill -9` или `APP_PORT=8081 ./run.sh` |
| `PostgreSQL недоступен` при старте | Запустите сервер БД (`brew services start postgresql@16`) или проверьте `DATABASE_URL` |
| Нужно начать с чистой базы | `dropdb bank_intelligence` — база и таблицы создадутся заново при следующем запуске |
| Хочу запустить в контейнере | `docker compose up` — поднимает и приложение, и PostgreSQL 16 (данные в томе `pgdata`) |

## atm_monitor (встроен)

`atm_monitor/` — часть проекта, отдельно ничего запускать не нужно: `./run.sh`
поднимает сервер и фоновый сборщик, который раз в час опрашивает
monitoring.btech.uz (раз в 15 минут) и пишет данные в схему `atm_monitor` основной базы
PostgreSQL. Для работы задайте `AUTH_USERNAME` / `AUTH_PASSWORD` в `.env`.

После каждого опроса обновляются история (изменения состояний, фактические
инкассации, суточные итоги, доступный остаток без неисправных кассет) и
рекомендации инкассации. Методика плана инкассаций, срочности 1–10 и расчёта
экономии — в [`docs/ekonomiya-inkassatsii.md`](docs/ekonomiya-inkassatsii.md).

- Страница «Менеджер банкоматов»: `/dashboard/atm-monitor.html`
- Живой баланс и кассеты автоматически появляются на карте и в списке ATM
- Опрос вручную: `POST /api/atm-monitor/poll`; один опрос без сервера: `python -m atm_monitor`
- Инкассации из карточек банкоматов собираются автоматически раз в 6 часов; один банкомат вручную: `python -m atm_monitor.encashments <id>`
- Модуль данных: карточка на главной, `/dashboard/data-console.html` (просмотр всех таблиц, полнота по датам, догрузка) и карточка банкомата `/dashboard/atm-card.html?id=<id>`. При `AUTH_DISABLED=1` открывается без входа, при включённом входе доступен только администратору

### Прогноз снятий (XGBoost)

`atm_monitor/forecast.py` по почасовым остаткам BTech считает суточные снятия
каждого банкомата и обучает XGBoost (лаги, скользящие средние, день недели,
дни зарплаты, праздники). Модель переобучается **ежедневно в 00:00** по
`TIMEZONE` (пропущенный из-за сна машины прогон выполняется сразу после
пробуждения), вручную — кнопкой «Переобучить» на странице аналитики или
`POST /api/analytics/forecast/run`.

Результат — снятия на 7 дней вперёд, время достижения low-cash и нуля,
рекомендуемая загрузка. Его используют страница аналитики и маршруты/календарь
инкассации (`hours_to_low_cash`). Пока истории меньше ~14 дней, XGBoost не
обучается, и прогноз строится запасным методом (среднее за последние дни или
скорость расхода от BTech); это видно на странице в блоке «Модель».

| Переменная | По умолчанию | Назначение |
|---|---|---|
| `ATM_FORECAST` | `1` | `0` — не запускать ежедневное переобучение |
| `FORECAST_HOUR` | `0` | Час переобучения (местное время `TIMEZONE`) |
| `FORECAST_DAYS` | `7` | Горизонт прогноза, дней |
| `FORECAST_HISTORY_DAYS` | `120` | Сколько дней истории брать для обучения |

## Структура проекта

```
api/
  main.py                  # единое FastAPI-приложение (оба домена)
  core/
    config.py              # DATABASE_URL, пул соединений, бизнес-пороги ATM
    db.py                  # пул PostgreSQL, создание схемы (init_db), репозиторий ATM и филиалов
    importer.py            # парсер XLSX реестров ATM и филиалов
    incassation_router.py  # региональные маршруты инкассации
    cashier_analytics.py   # фасад совместимости для домена кассиров
    cashier/
      helpers.py           # нормализация строк, разбор HR-статусов
      parsers.py           # парсер Excel/CSV отчёта KPI
      repository.py        # схема и сохранение данных кассиров
      analytics.py         # расчёт нагрузки, БЭК/ФРОНТ, выборки
dashboard/                 # статические страницы обоих модулей
migrations/schema.sql      # справочная схема PostgreSQL (таблицы создаются автоматически)
migrations/sqlite_to_postgres.py  # перенос данных из старой SQLite-версии
tests/                     # pytest (работают на отдельной базе bank_intelligence_test)
legacy/                    # исторические скрипты сбора данных по ATM
samples/                   # примеры Excel-файлов
```

```bash
pytest
```

Тесты, которым нужна база, используют отдельную базу
`TEST_DATABASE_URL` (по умолчанию `postgresql://localhost:5432/bank_intelligence_test`,

## ИИ-помощник (страница «Экономия»)

Круглая кнопка справа снизу на `/dashboard/savings.html` открывает объяснение экономии и чат.
Модель — строго `z-ai/glm-5.3-flash`, провайдер — строго `relace/fp4` через OpenRouter
(без запасных провайдеров); ключ — `OPENROUTER_API_KEY` в `.env`.

**Никакие данные проекта не уходят в модель:**

* Модель не видит ни одного числа и названия. Она пишет ответ с плейсхолдерами
  (`{{saving_month}}`, `{{freed_cash}}`…), а реальные значения подставляет браузер —
  они приходят с нашего сервера и в OpenRouter не отправляются.
* В вопросах пользователя любые числа, e-mail, телефоны, ссылки и все названия из базы
  (TID, адреса, филиалы, ФИО, логины) заменяются на `[число]`, `[скрыто]` и т.п.
  Под каждым вопросом видно, что именно ушло в ИИ.
* Запрос идёт только к провайдерам без сбора и хранения данных
  (`data_collection: deny`, `zdr: true`), без user-id и заголовков с названием сайта.
* Рекомендуется также выключить логирование запросов в настройках приватности аккаунта OpenRouter.

## Авторизация и роли

**По умолчанию вход выключен** — все страницы и API открыты без логина.
Чтобы включить вход и роли, задайте `AUTH_DISABLED=0` в `.env`.

При включённом входе при первом запуске (пустая таблица `users`) создаётся пользователь `admin` со
случайным паролем — он печатается в лог и сохраняется в файл
`data/admin_credentials.txt` (в `.gitignore`, в git не попадёт). Смените
пароль сразу после первого входа: `/admin` → Пользователи.

Права выдаются не на отдельный HTML-файл, а на функциональный блок (`atm_map`,
`atm_analytics`, `treasury`, `hr_cashiers`) — какие блоки видит роль, задаётся
в самой роли и редактируется в админ-панели (`/admin`, вкладка «Роли»), а не в
коде. Стартовые роли: `admin` (всё), `atm_manager` (карта/инкассация),
`treasury` (касса филиалов), `hr_analyst` (кассиры), `viewer` (без прав по
умолчанию) — админ может их переименовать, изменить состав страниц или
добавить свои.

Вход включается через `AUTH_DISABLED=0` в `.env`.
